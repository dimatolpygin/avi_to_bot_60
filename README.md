# SBAvito — ИИ-боты для Авито с интеграцией в amoCRM

ИИ-чат-боты для аккаунтов Авито: ведут диалог как живой продавец, отвечают по
товарам/услугам строго из прайса (без вранья по ценам и наличию), доводят до контакта
и заводят сделку с задачей менеджеру. Транспорт — собственная интеграция
Avito Messenger API ↔ amoCRM Chat API (несколько аккаунтов на одном сервисе).

## Ключевые принципы
- **Качество поиска = качество продукта.** Всё остальное работает поверх поиска, который нашёл верную позицию; после каждой правки словарей и весов — прогон замеров.
- **Цены и наличие — только через инструменты** (function calling), никогда «по памяти». Нет позиции → честно «нет», без подстановки похожего наугад.
- **Наличие — явный флаг**: пустой остаток не выкидывает позицию из каталога.
- **Прайс и промпты редактируются через веб-панель** на каждый аккаунт (промпт + база знаний + прайс раздельно).
- **Контакт бот не выпрашивает.** Клиент оставил телефон сам — лид уходит менеджеру вместе с выжимкой разговора: номер без контекста переписки менеджеру бесполезен.
- Ядро диалога отделено от транспорта: обкатка в Telegram → тем же ядром подключается Авито.

## Стек
Python 3.12 · aiogram · SQLAlchemy 2.0 (async) + Alembic · asyncpg · Redis ·
stdlib logging + contextvars (лог на русском со сквозным request-id) ·
OpenRouter (`anthropic/claude-haiku-4.5`) · своя React-панель · Docker.

## Структура
- `bot/` — приложение: `config.py`, `logger.py`, `db.py`, `cache.py`, `models.py`, `seed.py`,
  `main.py` (супервизор ботов), `proverka.py`, `core.py` (ядро диалога без транспорта),
  `profili.py` (персона и промпт на аккаунт), `pamyat.py` (история диалога в Redis),
  `lead.py` (контакт клиента и выжимка диалога → `leads`, дальше в amoCRM),
  `probe_dialog.py` (прогон диалога по любому аккаунту).
- `bot/channels/` — транспорты: `telegram.py` (три бота обкатки), на этапе 14 добавится Авито.
- `bot/etl/` — импорт прайса: `chtenie.py` (прочитать и проверить файл), `razbor.py`
  (атрибуты из названия), `import_prays.py` (upsert по артикулу одной транзакцией).
- `bot/search/` — поиск: `normalize.py` (нормализация и стемминг), `fuzzy.py` (опечатки),
  `slovari.py` (словари домена и резолв по ним), `zapros.py` (разбор запроса клиента),
  `katalog.py` (товары в памяти, группировка по длинам), `search.py` (скоринг и каналы),
  `probe.py` (прогон запросов через поиск), `baseline.py` (замер качества по трём наборам).
- `bot/ai/` — ИИ-слой: `openrouter.py` (клиент модели), `agent.py` (системный промпт,
  инструмент `search_products`, предохранители, agent-loop), `stil.py` (чистка стиля кодом),
  `probe.py` (прогон реплик через агента).
- `bot/chelovek/` — очеловечивание: `razbivka.py` (дробление ответа на реплики и живые
  задержки), `dispetcher.py` (дебаунс, прерываемость, отправка порциями), `probe.py`
  (сценарии проверки). Транспорта не знает — работает через колбэки канала.
- `migrations/` — миграции Alembic (схема `sbavito`, таблица версий там же).
- `data/` — словари поиска (правятся руками, подхватываются рестартом) и три набора запросов
  для замера: золотой, слепой, абстейн.
- `docs/07_ROADMAP.md` — дорожная карта по этапам, `docs/STATUS.md` — текущее состояние,
  `docs/BASELINE.md` — последний замер качества поиска (генерируется, руками не правится).

## Разработка
Postgres и Redis — существующие контейнеры хоста (`postgres16` :5432, `redis` :6379):
compose поднимает только приложение и ходит в них через шлюз хоста.

Три Telegram-бота обкатки (по одному на аккаунт Авито) поднимаются самим процессом:
токены лежат в `.env` (`TG_TOKEN_SAUNAMART`, `TG_TOKEN_SBSAUNA`, `TG_TOKEN_DESHMAN`),
пустой токен просто выключает своего бота. **Правка `.env` требует пересоздания
контейнера** (`docker compose up -d --force-recreate app`): переменные окружения
фиксируются при его создании, и автоперезагрузка кода их не обновляет.

```bash
cp .env.example .env               # заполнить PG*, REDIS_URL, ключи
docker compose up -d --build       # entrypoint сам гонит alembic upgrade head
docker compose exec app python -m bot.seed       # 3 аккаунта + заглушка промпта
docker compose logs -f app                       # подключения и события на русском
docker compose exec app python -m bot.proverka   # самопроверка: схема, логи, сквозной id
docker compose exec app pytest                   # тесты
```

Импорт прайса (идемпотентный, ключ синхронизации — артикул):
```bash
docker compose exec app python -m bot.etl.import_prays                 # файл по умолчанию
docker compose exec app python -m bot.etl.import_prays <файл> <аккаунт>
docker compose exec app python -m bot.etl.import_prays --tolko-razbor  # прогон без БД
```
Прайс — выгрузка гугл-таблицы заказчика; свежая кладётся поверх старой, путь по умолчанию
задан в `bot/etl/import_prays.py`. `--tolko-razbor` показывает, что распозналось из названий,
и ничего не пишет в БД — им проверяют правки разбора на живом файле. Повторный импорт того же
файла обязан дать 0 добавлено / 0 обновлено; исчезнувшая из прайса позиция гасится,
но остаётся в каталоге.

Разбор запроса клиента (словари домена, БД не нужна):
```bash
python -m bot.search.zapros                      # проверочный набор этапа 5
python -m bot.search.zapros "вагонка сорт б"     # свой запрос
```
Показывает норму, стемы и распознанные атрибуты: семейство и канал резолва
(точно / синоним / опечатка), сорт, породу, длину, габарит двери, объём и мощность печи,
артикул, маркер чужого домена. Словари — четыре json в `data/`; правка подхватывается
рестартом процесса, кода трогать не надо.

Поиск по каталогу:
```bash
python -m bot.search.probe                       # проверочный набор этапа 6
python -m bot.search.probe "липа 3 метра"        # свой запрос (каталог из файла прайса)
python -m bot.search.probe "липа 3 метра" --iz-bd  # то же поверх products в БД
```
Выдача — товары, а не строки прайса: 141 строка это 41 товар, размноженный по длинам.
Канал в шапке ответа показывает, чем нашли (артикул / точно / синоним / опечатка / порода /
название) или почему пусто: «чужой домен» = не наш профиль, «не найдено» = такого нет.
Оба источника каталога обязаны давать одинаковую выдачу — расхождение значит, что импорт
и файл разошлись.

Замер качества поиска — **гонять после каждой правки словаря, весов или логики поиска**:
```bash
python -m bot.search.baseline            # сводка по трём наборам + дельта к прошлому замеру
python -m bot.search.baseline --podrobno # плюс выдача по каждому расхождению
python -m bot.search.baseline --save     # записать docs/BASELINE.md как новую точку отсчёта
python -m bot.search.baseline --iz-bd    # каталог из products, а не из файла прайса
```
Три набора в `data/`: **золотой** (правильный ответ выверен по прайсу глазами, ворота — top-1
≥ 90%), **слепой** (разговорные формулировки, меряется семейство в топ-1, порога нет),
**абстейн** (чужой домен, ответ обязан быть пустым, ворота — ≥ 90%). Команда возвращает 1,
если ворота не пройдены **или** метрика просела относительно `docs/BASELINE.md`: порога мало,
потеря пары запросов из сорока ворота проходит, а клиента теряет. Метрика упала — правку
откатить или починить. Провал из живого диалога дописывается в `data/zolotoy_nabor.json`
и остаётся там навсегда.

ИИ-агент (ходит в OpenRouter, тратит деньги — прогон набора стоит примерно один цент):
```bash
python -m bot.ai.probe                 # набор реплик из критериев приёмки этапа 8
python -m bot.ai.probe "есть штиль?"   # своя реплика (несколько подряд идут одним диалогом)
python -m bot.ai.probe --dialog        # живой диалог в консоли
```
Каждый ответ проверяется кодом: длинное тире, markdown, эмодзи, простыня столбиком,
выпрашивание телефона и **сверка каждого числа из ответа с прайсом** — модель может назвать
правдоподобную несуществующую цену, и на глаз это не ловится. Цену, наличие и длины агент
берёт только из инструмента `search_products`; если он заявил, что товара нет, ни разу
не вызвав поиск, срабатывает предохранитель и поиск форсируется (в логе `🧯`, затем `🔧`).

Диалог по любому из трёх аккаунтов, неинтерактивно (ходит в OpenRouter, тратит деньги):
```bash
python -m bot.probe_dialog saunamart "почём липа 3 метра" "а сорт б"
python -m bot.probe_dialog sbsauna --fayl scenariy.json
python -m bot.probe_dialog saunamart --pachkoy "дверь" "печь" "ольха"
```
То же ядро, что у живых ботов (память, поиск, очеловечивание), но реплики клиента подаются
списком, а канал печатает расшифровку с секундомером. История — в процессе, живые диалоги
в Redis не затрагиваются. `--pachkoy` шлёт реплики не дожидаясь ответа: так проверяются
склейка и прерывание. Этим гоняют аккаунты после правки промптов — по одному прогону
на сценарий из отчёта.

Очеловечивание — как переписка идёт во времени (сети и денег не требует):
```bash
python -m bot.chelovek.probe            # четыре сценария в реальном темпе (~2 мин)
python -m bot.chelovek.probe --bystro   # то же ускоренно, просто увидеть ход
python -m bot.chelovek.probe --zhivoy   # живой чат в консоли поверх ИИ (тратит деньги)
```
Сценарии показывают то, за что отвечает слой: ответ не приходит мгновенно, длинный ответ
идёт двумя-тремя репликами с индикатором набора, три быстрых сообщения клиента склеиваются
в один вопрос, а новое сообщение отменяет недосказанный ответ — и в историю попадает ровно
то, что клиент успел увидеть. Слева в выводе секундомер: по нему видно разброс пауз.
Диспетчер не знает про транспорт, `Kanal` — это колбэки «отправить» и «печатает».

Правка любого `.py` в `bot/` перезапускает процесс автоматически (watchmedo).
`LOG_LEVEL=debug` добавляет в лог промпт и ответ модели.

Работа со схемой:
```bash
docker compose exec app alembic revision --autogenerate -m "что меняем"
docker compose exec app alembic upgrade head
docker compose exec app alembic downgrade -1
docker compose exec app alembic check              # есть ли дрейф моделей и БД
```

## Ветки
- `dev` — разработка. `master` — автодеплой (GitHub Actions), мерж только по явному решению.

## Безопасность
Репозиторий публичный: ни одного секрета в коде/истории. `.env` — в `.gitignore`,
секреты — в GitHub Secrets. Плейсхолдеры — в `.env.example`.
