# Дорожная карта реализации — SBAvito

Путь до прод-готовности. Каждый этап заканчивается **демонстрируемым результатом**
(что можно потрогать руками). MVP-first: сначала данные и ядро диалога на Telegram-песочнице,
транспорт Авито + amoCRM — в финале.

> **Прогресс всех этапов** — в [`STATUS.md`](STATUS.md). Внутри каждого этапа ниже —
> чекбоксы acceptance-пунктов. Закрытие этапа → git-тег `stage-N-done`.

## 🎯 Главное в системе — поиск по товарам и услугам

**Качество поиска = качество продукта.** Всё остальное (промпт, очеловечивание, CRM, панель)
работает только поверх поиска, который нашёл правильную позицию. Старый бот клиента провалился
именно здесь: врал про наличие, путал сорта, вываливал прайс — потому что не умел выбрать
одну верную строку.

Из этого три постоянных правила, действующих **все этапы, а не только этап 7**:

1. **После каждой правки словаря, весов или логики поиска — прогонять `baseline`.**
   Метрика упала → правка откатывается или чинится, а не «потом посмотрим». Так велась работа
   в telewin, и там это единственное, что удержало качество на 12 000 позиций.
2. **Поиск детерминирован, ИИ — нет.** Если бот ответил «не найдено», а поиск вернул позиции —
   это баг агентского слоя, а не поиска. Разбираться в `bot/ai/`, не в `bot/search/`.
   Обратное тоже верно: пустая выдача поиска на реальный товар чинится словарём, а не промптом.
3. **Каждый провал из живого диалога идёт в золотой набор.** Клиент прислал переписку, где
   спрашивали «штиль» и «плитку гималайской соли» — такие кейсы становятся тестами навсегда,
   чтобы регресс их не вернул.

Этап 7 (eval-харнесс) — не разовая работа, а инструмент, которым пользуемся до конца проекта.

  Этого в telewin нет сознательно, у нас — в скоупе.

**Решения по стеку** (обоснование в `06_ии_ядро.md`):
- Python 3.12 · aiogram · SQLAlchemy 2.0 (async) + **Alembic** · asyncpg · redis-py · httpx.
- Логи — stdlib `logging` + `contextvars` (сквозной request-id), на русском, «каждая щель».
- ИИ — OpenRouter `anthropic/claude-haiku-4.5`, function calling.
- БД и Redis — **существующие контейнеры** `postgres16` (:5432) и `redis` (:6379),

  В общем `postgres16` расширения `vector` и нет, а менять его образ нельзя (соседние проекты).
  Если замеры этапа 7 покажут провалы — вектор заводится отдельным этапом, схема к этому готова.

## Этап 3 — Схема БД + Alembic

**Цель**: полная схема в отдельной схеме `sbavito`, поднимаемая версионированными миграциями,
с автоприменением при старте контейнера.

**Что делаем**:
- SQLAlchemy 2.0 модели, Alembic с `version_table_schema='sbavito'`, `include_schemas=True`.
- Прайс: `accounts`, `products` (article, name, family, grade, species, length_m, unit,
  price_apiece, price_per_m, availability, characteristics, is_active), `product_aliases`, `price_meta`.
- Промпты и знания: `prompt_base`, `account_prompts`, `knowledge_blocks`, `faq`.
- Диалоги и лиды: `dialogs`, `messages`, `leads` (для панели, статистики и amoCRM).
- Enum: `account_kind` (goods/services), `availability` (in_stock/out/unknown), `price_unit` (piece/linear_m).
- Индексы: GIN trigram (`pg_trgm`) по `products.name` и `product_aliases.alias`, btree по `article`, `family`.
- Сиды: 3 аккаунта (`saunamart`, `sbsauna`, `sbsauna_deshman`) + заглушка `prompt_base`.
- Entrypoint контейнера прогоняет `alembic upgrade head` до старта бота.

**Критерии приёмки** (закрытие → tag `stage-3-done`):
- [ ] `alembic upgrade head` на чистой схеме создаёт все таблицы и enum без ошибок.
- [ ] Изменение модели → `alembic revision --autogenerate` рождает непустую миграцию (автогенерация живая).
- [ ] `alembic downgrade -1` откатывает последнюю миграцию без ошибок.
- [ ] `SELECT code, kind FROM sbavito.accounts` показывает ровно 3 аккаунта; повторный сид не плодит дубли.
- [ ] Колонка `availability` по умолчанию `unknown` — пустой остаток не превращается в «нет».

## Этап 4 — ETL прайса Saunamart

**Цель**: CSV клиента лежит в БД разобранным на атрибуты, повторный импорт ничего не ломает.

**Что делаем**:
- `bot/etl/csv_parser.py`: чтение CSV (`article, nomenclature, characteristics, price_apiece,
  price_per_meter, Наличие`), из названия вытаскиваются семейство, сорт, порода, длина `L-2.5 м`,
  габариты дверей, мощность/объём печей.
- Единица: заполнен `price_per_meter` → `linear_m`, иначе `piece`. Наличие: `Да`→in_stock,
  `Нет`→out, **пусто→out** (клиент подтвердил, что ведёт колонку сам), позиция остаётся в каталоге.
- **Источник правды по цене — `price_apiece`; цена за метр ВЫЧИСЛЯЕТСЯ** как `цена_шт / длина`,
  а не читается из колонки. Проверено на файле: инвариант `цена_шт = цена_м × длина` сходится
  на 99 строках из 111, а расходятся ровно 12 — вагонка сорта А от 1.9 до 3.0 м, где формула
  делит на фиксированные 1.8 (ошибка до 67%). Вычисление лечит это само и переживёт новые поломки.
- Рабочая ширина — **только из скобок в названии** (`15х95 (88)` → 88 мм). У полка (`26х90`)
  скобок нет: 90 — полная ширина, полок кладут с зазорами, рабочей ширины у него не существует.
  Позиция без скобок → поле пустое, пересчёт в м² для неё запрещён.
- Позиции с фасовкой в названии (`Фольга алюминиевая 12 м2`, `уп.10кг`) помечаются как упаковка —
  цена за упаковку целиком, делить нельзя.
- Идемпотентный upsert по **артикулу** (проверено: 141 артикул, дублей нет), diff-счётчики
  insert/update/skip/delete, всё в одной транзакции.
- Валидация до записи: минимум строк, обязательные колонки, битый файл → ошибка, БД не тронута.
- `price_meta` — дата актуальности прайса из mtime/имени файла.

**Критерии приёмки** (закрытие → tag `stage-4-done`):
- [ ] Импорт кладёт 141 позицию, `SELECT count(*)` сходится; уникальных семейств — 41 группа по названию.
- [ ] Повторный запуск на том же файле даёт 0 insert / 0 update / 0 delete (идемпотентность).
- [ ] У позиции «Вагонка Липа сорт А 15х95 (88) L-2.5 м» в БД: сорт `А`, порода `липа`, длина `2.5`, цена 428.
- [ ] Позиция с пустым наличием попадает в БД со статусом «нет в наличии», а не пропадает из каталога.
- [ ] У «Вагонка Липа сорт А L-3.0 м» цена за метр в БД равна **171**, а не 285 из колонки файла.
- [ ] Импорт логирует ровно 12 строк с расхождением инварианта (вагонка сорта А, 1.9–3.0 м)
      и берёт вычисленное значение, а не файловое.
- [ ] У вагонки липы рабочая ширина 88, у вагонки ольхи 80, **у полка — пусто** (скобок в названии нет).
- [ ] Фольга и камни в упаковке помечены как «продаётся упаковкой».
- [ ] Битый/обрезанный CSV не изменяет ни одной строки в БД и падает с понятной ошибкой.
- [ ] Дата прайса читается из `price_meta`, а не захардкожена.

## Этап 5 — Словари и нормализация

**Цель**: клиент пишет как хочет — «сорт б», «трёхметровая липа», «доска на полок» — и это
сводится к позициям прайса.

**Что делаем**:
- `bot/search/normalize.py` — переносим из telewin: `norm()` (гомоглифы латиница→кириллица, ё→е),
  `stems()` (snowball russian + стоп-слова), `soft_has()` (префиксный матч ≥4 символов).
- `data/slovar_svodnyy.json` — ~15 семейств под баню: вагонка, полок, дверь, печь, наличник,
  брус, рейка, фольга, камни, плитка соли, короб вентиляции, спил можжевельника. Ключ + канон + синонимы.
- **Обязательно: `сорт Б` ≡ `сорт В`.** В прайсе строки называются «сорт В», клиент и менеджер
  в переписке пишут «сорт Б» (кириллическая В читается как латинская B). Без маппинга бот скажет «нет такого».
- `data/sleng_razmerov.json` — «трёхметровая»→3.0, «двушка»→2.0, «полторашка»→1.5, размеры дверей.
- `data/chuzhoy_domen.json` — маркеры не нашего профиля (инструмент, бытовая техника, еда, одежда).

**Критерии приёмки** (закрытие → tag `stage-5-done`):
- [ ] «вагонка сорт б» и «вагонка сорт в» дают один и тот же набор позиций.
- [ ] «трёхметровая липа» распознаётся как длина 3.0 м.
- [ ] «болгарка», «холодильник», «шампунь» отсекаются гейтом чужого домена до поиска.
- [ ] Опечатка «вогонка» находит вагонку (фаззи-канал с порогом 0.85).
- [ ] «полог» и «полок» ведут к одному семейству (народное написание).
- [ ] Правка словаря подхватывается перезапуском без изменения кода.

## Этап 8 — ИИ-ядро: промпт + инструменты

**Цель**: бот отвечает как живой продавец из скрина клиента — короткой вилкой, без вранья по прайсу.

**Что делаем**:
- `bot/ai/agent.py` — системный промпт под баню на структуре telewin: персона живого продавца,
  ассортимент, «КАК РАБОТАТЬ», жёсткие правила по данным, «КАК ТЫ ОБЩАЕШЬСЯ», антипримеры
  из `04_баги_старого_бота.md`. Правила поведения — в промпте, не в прайсе.
- Инструмент `search_products(query, assortiment)` — адаптивный лимит 8/15.
- **Предохранитель `_zayavil_otkaz`**: регексп ловит отказ в ответе модели; если поиск не вызывался —
  форс-повтор с `tool_choice=required`. В telewin без него был баг «то есть, то нет». Не убирать.
- `bot/ai/openrouter.py` — haiku-4.5, temperature 0.2, таймаут 60с, 3 ретрая на 429/5xx.
- `bot/ai/stil.py` — постобработка: убрать «—» и markdown кодом, а не промптом.
- Agent-loop до 4 итераций; промежуточные tool-сообщения в память диалога не пишем.

- [ ] В ответах нет длинного тире, markdown, эмодзи и списков столбиком.
- [ ] Бот не просит телефон по своей инициативе.

## Этап 9 — Очеловечивание

**Цель**: переписка выглядит как с человеком, а не с формой ответа.

**Что делаем** (паттерны из `vk0043/humanize.py`):
- Дробление длинного ответа на короткие реплики с плавающим порогом.
- Задержки: чтение 2–5 с, набор ~9–13 с по длине, пауза между репликами; всё время статус «печатает».
- Дебаунс: несколько быстрых сообщений клиента склеиваются в один ответ.
- Прерываемость: новое сообщение отменяет текущую генерацию; в память кладём только реально отправленное.

**Критерии приёмки** (закрытие → tag `stage-9-done`):
- [ ] Три сообщения подряд за 5 секунд → один связный ответ, а не три.
- [ ] Длинный ответ приходит 2–3 репликами с паузами, статус «печатает» виден между ними.
- [ ] Сообщение во время генерации отменяет её; отменённый текст не попадает в историю диалога.
- [ ] Задержки не фиксированные — разброс виден в логах.
- [ ] Склейка, прерывание и отправка каждой реплики видны в логе с request-id.

## Этап 10 — Три Telegram-бота

**Цель**: три бота на трёх токенах имитируют три аккаунта Авито, каждый со своими данными и промптом.

**Что делаем**:
- `bot/core.py::Yadro.obrabotat(account, chat_key, text, typing_cb)` — доменная логика без транспорта,
  замок `asyncio.Lock` на `(аккаунт, чат)`.
- `bot/channels/telegram.py` — тонкий адаптер; `bot/main.py` — `asyncio.gather` под супервизором,
  падение одного бота логируется и перезапускается, соседи живы.
- Аккаунт = токен + прайс + промпт + база знаний. Пустой токен → бот не поднимается.
- Сессии Redis: ключ `sbavito:dialog:{аккаунт}:{chat}`, TTL 30 мин, последние 12 сообщений.

**Критерии приёмки** (закрытие → tag `stage-10-done`):
- [ ] Три бота отвечают одновременно, каждый под своим именем.
- [ ] Saunamart отвечает по прайсу товаров; боты услуг на тот же вопрос отвечают своими данными.
- [ ] Один и тот же chat_id в разных ботах не смешивает истории диалога.
- [ ] Убийство одного бота не роняет двух других (видно в логе супервизора).
- [ ] `/reset` очищает историю только текущего бота.
- [ ] Пустой токен в `.env` выключает конкретного бота, остальные работают.
